# CanIToolCall v0.1.0

**caniuse for tool calling.** CanIToolCall is a neutral conformance suite and compatibility matrix for the tool-call and reasoning parsers of open-weight models, across inference engines. It replays recorded raw model outputs (fixtures) through each engine's **own parser code**, offline, with no GPU and no model weights. It parses every output once without streaming and once for each way of splitting the stream into chunks. It also includes a live `probe` for any OpenAI-compatible endpoint.

- Matrix: https://redd34.github.io/canitoolcall/
- Results snapshot behind these notes: [`results/2026-09-25/`](https://github.com/redd34/canitoolcall/tree/main/results/2026-09-25), with every failing case triaged in `triage.jsonl`

- **Eight checks:** `expected_match`, `expected_error`, `stream_equals_nonstream`, `split_invariance`, `no_leakage`, `arguments_json`, `arguments_schema` and `parallel_order`. They run over seeded, token-level chunking strategies (`one`, `special`, `token`, `rand:k:8`). Engines whose servers stream one token per event are judged only on realistic strategies.
- **CLI:**
  - `canitoolcall run` replays fixtures through an engine.
  - `canitoolcall probe` checks a live OpenAI-compatible endpoint. It never sends an API key unless you configure one.
  - `canitoolcall matrix` builds the static site, with drill-down pages and a repro command for each failure.
  - `canitoolcall validate` checks fixtures against the spec.
  - `canitoolcall engines` lists the engine adapters.
- **A pytest plugin** (`canitoolcall.pytest_plugin.assert_conforms`) that engine maintainers can use to vendor the corpus. The wheel bundles the spec, the fixtures and the site templates.

## Headline findings

**Every engine tested has at least one tool-call parser bug.** These are the main bug classes. Each one was reproduced again on 2026-09-26 through the engine's own code path.

- **Multi-token streaming deltas lose tool calls.** Several parsers are correct without streaming and with one token per delta. They silently drop a call or its arguments when one delta carries several tokens, which happens with speculative decoding or server-side delta batching.
- **Format-marker text inside argument strings breaks parsing, in every engine.** For example, a JSON string argument containing `</tool_call>` makes a parser return no call, or leak the markup into content.
- **Type and value corruption.** Untyped nested numbers, `null` or exponent notation come back as strings, and whitespace or special-token text inside string values is stripped.
- **Template-derived parsing failures.** With some official Hub chat templates, as embedded in popular GGUFs, every tool call fails to parse.
- **Header-form gaps in Harmony (gpt-oss) parsing.** Valid Harmony header forms are not recognised, so text is dropped or markup leaks into content.

Every failing cell on the matrix links to its fixtures, the observed parse, the parser configuration and a one-line repro command. Upstream reports for the new findings are being filed with the engine projects. Where an issue already exists, the fixture is added to it as a comment.

## Known limitations

- **Offline parser replay only.** Behaviour that depends on a running server was reproduced through the engine's own code path, not observed on a live server. This covers stop-token handling, BOS, `skip_special_tokens` and delta batching. The one `engine_bug_candidate` (llama.cpp with Mistral and BOS) needs a live `llama-server` with real weights before anyone reports it.
- **`probe` has only been exercised against the in-repo mock OpenAI-compatible server,** not against a real engine and model. Reports from real stacks are very welcome.
- **The snapshot was run on macOS arm64.** The nightly workflow runs on Linux x86_64, and a few results depend on the CPU architecture. For example, Ollama's out-of-range int64 conversion saturates on arm64 and wraps on amd64. At release time, the nightly jobs for Ollama and Kimi K3 are still being fixed, so those cells on the live matrix may lag the snapshot.
- **Coverage gaps:**
  - llama.cpp has no Llama 4 coverage, because there is no authoritative ungated chat template.
  - DeepSeek-V4.1 is unsupported on SGLang and llama.cpp.
  - Ollama's legacy template `tools` parser is not covered: 208 fixtures are unsupported there.
  - transformers only covers Gemma 4, the only family whose Hub repo ships a `response_template`.
  - MiniMax and NVIDIA Nemotron are not covered yet.
  - Hosted APIs and LM Studio are out of scope for v0.1.
- **Spec gaps:**
  - There is no prompt or message-history field.
  - There is no `finish_reason` or stop-token field.
  - There is no per-fixture variant field, so Llama 3.x pythonic calls are not covered.
- **Open triage.** 50 failing cases are still `untriaged_discrepancy`.
- **Truncation policy.** A partial tool call for output cut by `max_tokens` counts as a failure, which is a deliberate spec choice. See `spec/README.md`.

## Contributing

Adding a model family takes a single PR: format notes, `family.json`, fixtures and a deterministic generator. Adding fixtures to an existing family, or a new engine adapter, also takes one PR each. [CONTRIBUTING.md](https://github.com/redd34/canitoolcall/blob/main/CONTRIBUTING.md) has the step-by-step guide and the provenance rules. Well-scoped starter tasks carry the [`good first issue`](https://github.com/redd34/canitoolcall/labels/good%20first%20issue) label.

The code is Apache-2.0. The fixture corpus quotes material under other licenses: each fixture records its license in `provenance.license`, and the full notices are in `THIRD_PARTY_NOTICES.md`. Built with Llama.
